# 会议同传台

英文会议实时同传辅助。开会时开着它，浏览器抓会议标签页的声音，左栏出“英文原句＋中文译文”的
双语笔录，右栏吸收会前背景文件，随时帮你拟英文回复并附中文对照。

## 跑起来

不需要任何环境变量，模型接入在界面里配。

```bash
cd ~/AIwork/03-AI项目/meeting-interpreter

# 首次准备
uv sync
cd web && npm install && npm run build && cd ..

# 开会时只要这一条
.venv/bin/python -m uvicorn server.main:app --host 127.0.0.1 --port 8787
```

然后在 Chrome 打开 http://127.0.0.1:8787 。改前端时用 `cd web && npm run dev` 开
5173 端口，接口会代理到 8787。

## 模型设置

首次使用点右上角“模型设置”，填两层。

文本层走 OpenAI 兼容的 `/v1/chat/completions`，负责底稿提炼、译文校正、右栏拟稿。填 base URL、
API key，以及两个 model name：快档在会议中拟稿用，要快；强档做底稿提炼和“换强模型重写”，要准。
填完点“拉模型清单”能看到这个 key 实际可用的模型。

语音层负责实时字幕。默认 `qwen3.5-livetranslate-flash-realtime`（阿里云百炼实时接口，音频进、
源语与译文文本一起出）。base URL 填百炼给的 `compatible-mode/v1` 地址即可，实时地址由程序换算。
Gemini Live Translate 那条也可选，留作备用。

三个“测试”按钮都是真发一次请求，不是本地校验。API key 只写进 `data/settings.json`（权限 600，
已在 `.gitignore` 里），保存后界面只显示是否已填。

## 底稿是怎么被吸收的

上传的文件抽成纯文本后**留在 data/docs/**，不是读一次就丢。三个层次同时起作用。

一是提炼摘要。强档模型读全部原文，抽出事项、当事人、争点、术语译法、我方立场与底线，存
`data/context.json`。摘要每次拟稿都在上下文里，我方立场排第一位。

二是原文全文进上下文。拟稿时把已存原文按字数上限直接放进提示词开头，模型能直接引用条款原话。
上限在模型设置里调，默认两万字。原文与摘要放在提示词最前面，是为了让服务端的上下文缓存命中同一
段稳定前缀，变动的最近对话与我的要求放最后。

三是向量检索兜住超出部分。原文超过上限时，按最近对话做相似度检索取最相关的三块补进上下文。检索
**不在拟稿的关键路径上**：它由会议过程中每段收口后的后台任务预取，拟稿时直接取用。实测把这一次
向量往返移出关键路径，首字从 4.13 秒降到 2.39 秒。向量存 `data/index.json`，纯 Python 算余弦，
没有引向量数据库。

上传是**累加**：新文件并进已存原文，旧的还在，摘要按全部原文重算。要去掉某一份点它旁边的删除，
要整份重来点清空全部底稿。

## 开会流程

1. 会前点右上角“会议底稿”，把背景文件拖进去，再补一句我方立场与底线。系统会读出当事人、
   争点、术语译法，并生成术语锁定规则。
2. 会议用 Zoom 或 Teams 的**网页版**打开（这一点必须遵守，见下）。
3. 点“开始记录”，Chrome 弹出共享面板时选“Chrome 标签页”，选中会议那个标签页，
   并打开“同时分享标签页音频”。
4. 左栏出双语笔录。右栏输入要求，回车发出，拿到英文回复直接念，或按“换强模型重写”精修。
5. 点“停止记录”。记录已经落在 `data/meetings.db`，需要成文时取
   `GET /api/meetings/<id>/export.md` 。

## 声源为什么必须是网页版会议

Chrome 在 macOS 上通过屏幕共享接口只能拿到浏览器标签页的声音，拿不到 Zoom、Teams 桌面端
应用的声音。要覆盖桌面端，需要装 BlackHole 一类虚拟声卡并配多输出设备，属于要先征得同意的
系统改动，本项目暂未走这条路。录音条上的声源可以选“麦克风”或“混合声源”，后者把标签页
声音与你自己的麦克风一起送进去。

## 术语锁定怎么工作

实时翻译那条流不接受文字指令，没法把术语表喂给模型，所以译文出来之后再按表校正。规则来自
会前底稿：首选译法、模型可能吐出的其他说法，以及程序自动展开的并列短语组合（“陈述与保证”
“声明和担保”这类写法会一并收进首选译法，三个连词“和”“与”“及”视为等价）。

规则表存在 `data/context.json`，可以直接手改 `terms` 里的 `zh` 与 `variants`，改完在
“会议底稿”里点“重新读取 data/context.json”即可生效，不必重新上传文件。

自动生成的 variants 偶尔会过宽，例如把 escrow 的变体写成“托管账户”，于是“托管账户”会被
改成“第三方托管”。发现这类误替换时，删掉 `data/context.json` 里对应的那一条。

## 能读什么文件

- **PDF 三级降级**：先 pypdf，文字太少换 pdftotext（poppler），还是太少就当扫描件走 OCR
  （pdftoppm 渲染加 tesseract 认字，中英一起认，最多认前 40 页）。外部工具没装就跳过该级。
- **加密 PDF**：只有空密码能自动处理，其余明确提示先去掉密码，不会静默失败。
- **损坏或空白 PDF**：单独报错并说明原因，不影响同批其他文件入库。
- **Word**：.docx 直接读（含表格），老式 .doc 走 macOS 自带 textutil 转换。
- **文本**：按 utf-8、gb18030、utf-16 依次试，国内来的 GBK 文件不会变乱码。
- **单页解析失败**不会拖垮整份文件，跳过该页继续。

OCR 依赖 `tesseract` 与 `poppler`（提供 pdftotext、pdftoppm），本机已装。没装时扫描件会明确
提示读不了，不会崩。

## 自测

后端起着的前提下：

```bash
.venv/bin/python -m server.tests.replay          # 英文样例，看双语笔录与延迟
.venv/bin/python -m server.tests.replay --zh     # 中文样例，同语种只出一行
.venv/bin/python -m server.tests.replay --draft  # 拟稿接口，看首字延迟与中英分隔
python3 -m server.tests.ui_check                 # 界面渲染与音频接线，出截图
.venv/bin/python -m server.tests.extract_check   # 文件抽取对抗性测试，七类输入
```

`ui_check` 用系统 python（playwright 装在系统解释器上，不进项目依赖），跑之前要先
`npm run build`。

## 实测数据（2026-08-17，阿里云百炼）

语音层 `qwen3.5-livetranslate-flash-realtime`：

- 中文译文首次上屏 2.4 到 3.9 秒，英文原话首次上屏 6.6 到 6.7 秒。这条流译文比原话先到。
- 同语种（中文说话、译文也是中文）会自动只显示一行，不重复。
- 连通测试 3.9 秒拿到 `session.created`。

文本层：

- 底稿提炼（强档 `qwen3.8-max`，思考已关，走流式）：一份约六千字符的背景文件 9 到 10 秒完成，
  产出 55 条术语替换规则。
- 拟稿（快档 `qwen3.6-flash`，思考已关）首字延迟随上下文变化，实测四个点：一千五百字 1.6 秒，
  一万九千字 1.8 到 3.3 秒，两万字加一次同步检索 4.13 秒，两万字用后台预取片段 2.39 秒，
  四万字 5.05 秒。默认上限因此定在两万字。
- 向量：`text-embedding-v4` 与 v3 都可用，1024 维，两条文本 0.7 到 1.7 秒。三份原文共一万九千字
  切成 45 块。
- 检索有效性核验：只在第二份附件里出现的释放安排（第一周年 40%、第 18 个月释放余额），拟稿时被
  准确引用，没有编造。
- 大文件：五万五千字的 docx 正常入库，四份原文共七万四千字切成 140 块，索引重建 22 秒（批次
  并行前是 48.6 秒）。坏文件（伪造的 pdf）单独报错，不影响其他文件入库。

其他：

- 点“停止记录”后要等约 3.5 秒才收口最后一段，这是留给模型吐完尾巴的时间。
